# 認証の学習まとめ

## 1. 認証とは

認証（Authentication）とは、

> 「このユーザーは誰なのか」を確認すること

です。

認可（Authorization）は、

> 「そのユーザーに、この操作をしてよい権限があるか」を確認すること

です。

---

## 2. 最低限必要なもの

自前で認証を作るなら、まずは以下です。

```text
User
Session
Cookie
パスワードのハッシュ化
```

### User

```prisma
model User {
  id           Int       @id @default(autoincrement())
  email        String    @unique
  passwordHash String
  sessions     Session[]
}
```

パスワードそのものはDBに保存せず、

```text
パスワード
 ↓
ハッシュ化
 ↓
passwordHash
```

として保存します。

---

## 3. Sessionとは

Session（セッション）は、

> 「このユーザーは現在ログインしている」という状態をサーバー側で管理するもの

です。

```text
Session
id = abc123
userId = 5
expiresAt = 2026/10/01
```

つまり、

```text
abc123
 ↓
User ID 5
```

という関係です。

---

## 4. Cookieとは

Cookieは、

> ブラウザに保存され、後のリクエストと一緒にサーバーへ送られるデータ

です。

認証ではCookieに、

```text
sessionId=abc123
```

のようなSession IDを保存します。

---

## 5. CookieとSessionの関係

```text
【ブラウザ】

Cookie
sessionId=abc123
        ↓
        ↓ リクエスト
        ↓
【サーバー】

Session
abc123 → userId: 5
        ↓
User
id: 5
```

つまり、

> Cookieは「誰なのか」を直接持つのではなく、Sessionを探すためのIDを持つ

という構成です。

---

## 6. なぜUser IDをCookieに直接入れないのか

例えば、

```text
Cookie
userId=5
```

だけだと、クライアント側で値を変更される可能性があります。

```text
userId=5
↓
userId=6
```

と変更されると危険です。

そのため、

```text
Cookie
sessionId=ランダムな値
```

として、

```text
Session
ランダムな値 → userId 5
```

をサーバー側で管理します。

---

## 7. ログインの流れ

```text
① メールアドレス・パスワードを送信
        ↓
② DBからUserを探す
        ↓
③ パスワードを照合
        ↓
④ 正しければSessionを作成
        ↓
⑤ CookieにsessionIdを設定
```

---

## 8. ログイン後のページアクセス

```text
ブラウザ
 ↓
Cookie: sessionId=abc123
 ↓
サーバー
 ↓
Sessionを検索
 ↓
userId=5
 ↓
「この人はUser ID 5」
 ↓
ページを表示
```

---

## 9. 各ページでSessionを確認する

認証が必要なページ・処理では確認します。

```text
/pages
/pages/new
/pages/[id]
```

ただし、毎回同じ処理を直接書くわけではありません。

```ts
const user = await getCurrentUser();

if (!user) {
  redirect("/login");
}
```

のように、認証処理を共通関数にまとめます。

---

## 10. ログインページだけで確認するのでは不十分

ユーザーはログインページを経由せず、直接URLへアクセスできます。

```text
/pages
    ↓
Session確認

/pages/new
    ↓
Session確認

/pages/[id]
    ↓
Session確認
```

という考え方になります。

**ログインした事実を信頼するのではなく、認証が必要な処理を行う時点でSessionを確認します。**

---

## 11. Server Actionでも確認する

画面だけで認証チェックしても不十分です。

例えばページ削除などのServer Actionでも、

```text
フォーム送信
 ↓
Server Action
 ↓
Session確認
 ↓
認証・認可確認
 ↓
DB更新
```

とします。

理由は、画面を経由せず直接処理を呼び出される可能性があるためです。

---

## 12. Cookieのセキュリティ設定

| 設定 | 意味 |
|---|---|
| `HttpOnly` | JavaScriptからCookieを直接読めなくする |
| `Secure` | HTTPS通信のときだけCookieを送る |
| `SameSite` | 別サイトからのリクエスト時にCookieを送る条件を制御 |
| 有効期限 | Sessionをいつまで有効にするか |

例：

```ts
cookieStore.set("sessionId", sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: "lax",
  expires: expiresAt,
});
```

---

## 13. CSRF

CSRFは、

> ログイン中のユーザーを利用して、意図しない操作を実行させる攻撃

です。

対策として、

- `SameSite`
- CSRFトークン

などがあります。

---

## 14. その他の認証機能

### パスワードリセット
パスワードを忘れたユーザーが、メールなどを利用してパスワードを再設定できる機能。

- リセット用の一時トークンを発行
- ユーザーのメールアドレスにリセット用URLを送信
- トークンには有効期限を設定
- トークンは一度使用したら無効にする
- パスワードそのものをメールで送信しない

### メールアドレス認証
登録されたメールアドレスをユーザー本人が利用できることを確認する機能。

- 認証用の一時トークンを発行
- 登録したメールアドレスに認証用URLを送信
- URLアクセス時にトークンを検証
- 認証完了後、メールアドレスを認証済みとして管理する

### ログイン試行回数制限
パスワードを何度も試してログインを突破する攻撃（ブルートフォース攻撃）を防ぐための制限。

- 一定回数ログインに失敗した場合、一時的にログインを制限する
- 例：5回失敗した場合、10分間ログインできなくする
- ユーザーIDやメールアドレス、IPアドレスなどを基準に試行回数を管理する

### レート制限
短時間に大量のリクエストを送信することを防ぐための制限。

- 一定時間内に送信できるリクエスト数を制限する
- ログイン、パスワードリセット、メール送信などに適用する
- 大量アクセスによる不正操作やサーバーへの負荷を抑える

### 2段階認証
パスワードだけでなく、別の認証方法を組み合わせて本人確認を行う仕組み。

- パスワードによる認証
- 認証アプリなどによる確認コードの入力
- SMSやメールによる確認コードなど

パスワードが漏洩した場合でも、不正ログインされにくくする。

### GitHubログイン
GitHubアカウントを利用してログインできる機能。

- OAuthなどの仕組みを利用してGitHubと連携する
- ユーザー自身のパスワードをアプリ側で管理する必要がない
- 初回ログイン時にGitHubのユーザー情報とアプリのアカウントを紐付ける

### SSO
SSO（Single Sign-On）は、一度のログインで複数のサービスを利用できる仕組み。

- 認証を専用の認証サービスに集約する
- 認証サービスでログインすると、連携している複数のサービスを利用できる
- 企業内システムなどでよく利用される

## 一番大事な理解

> **Cookie → Session → User**

という3段階で、

> 「このリクエストは誰から来たのか」

を判断しています。
