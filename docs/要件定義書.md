# 要件定義書

## 社内ナレッジベース(簡易Wiki)システム

---

## 1. プロジェクト概要

### 1.1 背景

- 研修にてGit&GitHub、TypeScript、React、Next.js、Prismaを学習した
- HR企画部の月例報告会に参加した際、部署内における課題として「属人化」が挙げられていることを知った
- ナレッジ共有が個人に依存している現状に対し、以下の観点から改善の余地があると考えた
  - アウトプット(資料作成)の高速化
  - ナレッジの保存性向上
  - アクセスの簡易化
- 上記の課題感と、研修で得た知識・技術をアウトプットとして提示する必要があるという状況を踏まえ、これらを同時に満たすシステムとして社内向けナレッジベースの開発を発案した
- なお開発成果物については口頭ディフェンス(質疑応答)が実施されるため、実装だけでなく設計意図・技術選定理由を説明できる状態まで理解を深めて開発する必要がある

### 1.2 目的

研修で学んだ技術(Git&GitHub、TypeScript、React、Next.js、Prisma)の特性を活かし、以下を満たすシステムを開発する。

1. 各技術の特性(型安全性、コンポーネント設計、リレーショナルデータ管理、バージョン管理思想など)を活用した設計・実装を行うこと
2. HR企画部で確認された属人化の課題に対し、ナレッジ共有の効率化(アウトプットの高速化・保存性向上・アクセスの簡易化)に資するシステムであること
3. 開発工程・設計判断を通じて、口頭ディフェンスに耐えうる技術理解を得ること

本プロジェクトの主目的は「セキュアな本番システムを構築すること」自体ではなく、**実務で使われる技術・開発フローに関する知識と経験を得ること**にある。この前提は、後述するアクセス制御に関する判断(第5章)にも関わる。

### 1.3 開発対象システム

社内向け簡易ナレッジベース(Wiki)システム

Markdown形式による記事の作成・編集・検索機能に加え、編集履歴を保持する仕組みを持つ。Gitのバージョン管理思想を、記事の改訂履歴管理という形でアプリケーション設計に応用する。

また、ナレッジ記事の内容をもとに資料(スライド/ドキュメント)を作成する機能(資料構成支援)を備え、外部生成AI(Gamma API)との連携を想定した設計・実装を行う。

### 1.4 開発条件

- **開発期間**: 10日間(要件定義の詰め〜実装〜口頭ディフェンス準備まで。当初14日間だったが短縮。MVPスコープは変更せず、作業工程の統合によって日数を圧縮している)
- **開発体制**: 個人開発

## 2. 対象ユーザー

### 2.1 想定利用者

社内の全部署の社員を対象とするが、特に以下の部署での利用を主眼に置く。

- **HR企画部**: ナレッジ共有の課題(属人化)を直接抱えている部署であり、本システムの発案元。研修報告・業務ノウハウ・議事録等のナレッジ蓄積・共有に利用する
- **その他部署**: 部署内マニュアル、業務手順、FAQ等の共有用途を想定(全社展開時)

### 2.2 利用シーン

| シーン | 利用者の行動 |
|---|---|
| ナレッジの記録 | 業務ノウハウや会議内容をMarkdown形式で記事化し、著者を選択して保存する |
| ナレッジの参照 | 過去に登録された記事を検索・閲覧し、業務に活用する |
| ナレッジの更新 | 既存記事の内容が古くなった場合に編集し、新しい改訂として保存する |
| 属人化状況の把握 | 改訂履歴を見て「誰がどの記事を書いたか・更新したか」を確認する |
| 資料作成 | テンプレートに沿って内容を入力し、資料(記事)として整形・保存する。Gamma API経由で外部生成されたスライド/ドキュメントへの変換も可能(モック実装) |

### 2.3 想定利用環境

- ブラウザからアクセス可能なWebアプリケーションとしてVercel上にデプロイする(PC利用がメイン)
- 個別ユーザーのログイン機構は実装しない
- 本システムは研修成果物のプロトタイプであり、実運用を想定した厳密なアクセス制御(認証、社内ネットワーク限定等)は設けていない。これは本プロジェクトの主目的が実務知識の習得にあり、セキュアな本番システムの構築自体を目的としていないためである。本番導入する場合は、認証機能を含むアクセス制御の追加設計が別途必要になる

### 2.4 ユーザーの技術リテラシー

- Markdown記法に不慣れな非エンジニア層(HR企画部等)の利用を想定
- そのため、Markdown記法を意識せずに使えるよう、簡易ツールバーによる入力支援を必須要件とする(機能要件No.6と対応)

### 3.2 機能詳細(MVP)

#### 3.2.1 記事作成(No.1)

| 項目 | 内容 |
|---|---|
| 入力 | タイトル(必須)、本文(Markdown、必須)、著者(User選択、必須) |
| 処理 | Pageレコードを新規作成し、同時に初回のRevisionレコードを作成する |
| 出力 | 作成された記事の詳細画面へ遷移 |
| バリデーション | タイトル未入力・本文空・著者未選択の場合、保存ボタン自体を非活性にし送信不可(3.6参照) |

#### 3.2.2 記事編集(No.2)

| 項目 | 内容 |
|---|---|
| 入力 | 既存Pageの新しい本文(Markdown)、編集者(User選択、必須) |
| 処理 | Page本体は上書きせず、新規Revisionレコードを追加する。Pageの`updatedAt`のみ更新 |
| 出力 | 更新後の記事詳細画面。改訂履歴に新しいレコードが1件追加される |

### 3.3 記事削除を論理削除とした理由

物理削除ではなく論理削除を採用した理由は以下の通り。

1. **ナレッジ資産の保護**: 物理削除を行うと、リレーション上紐づく改訂履歴(Revision)も連鎖的に削除することになり、過去に誰が何を書いたかという記録ごと失われてしまう。これは本システムの目的そのものと矛盾する
2. **誤操作からの回復可能性**: 論理削除であれば、誤って削除した場合も`deletedAt`をNULLに戻すだけで復元できる
3. **将来の機能拡張余地**: 「削除済み記事の復元」のような機能を将来追加する場合も、データが残っているため設計変更なしに対応できる

論理削除の保守性上の注意点(クエリへの条件付与漏れリスク)と、その対策としての専用ライブラリ導入の検討については設計書1.4を参照。

### 3.4 見送った機能について

#### 3.4.1 差分表示(diff)を見送った理由

差分表示とは、改訂前後で「どの文章が追加・削除されたか」を色分けして表示する機能である。Revisionはスナップショット保存する設計のため、比較処理自体は既存ライブラリで容易に実現できるが、視覚的な差分表示UI・Markdown記法を考慮した表示・比較対象選択UIといった周辺実装コストが、10日間の開発期間に対して重いと判断し見送った。データモデルの変更は不要なため、将来UI層のみの追加で対応できる。

#### 3.4.2 バージョンロールバックを見送った理由

技術的には既存の編集機能を流用でき実装コストは低いが、「ロールバックという操作を履歴上どう扱うか」という仕様上の論点(同一内容のRevisionが複数並ぶ見え方、誤操作防止策、実行者を著者として記録することの妥当性)が整理しきれていなかったため見送った。

#### 3.4.3 本格的なWYSIWYGエディタを見送った理由

Tiptap等の導入・学習コストが高く、10日間のスコープでは投資対効果が見合わないと判断した。代わりにテキストエリア+簡易ツールバー+リアルタイムプレビューという組み合わせで対応している。

### 3.5 Markdown形式を採用する理由

記事本文の記述形式としてMarkdownを採用した理由は以下の通り。

1. **可搬性**: 特定のアプリケーションに依存しない軽量な記法であり、社内外で広く使われている
2. **研修技術との親和性**: Git/GitHubの学習過程でMarkdown記法に触れる機会が多く、技術的な一貫性を示しやすい
3. **入力の軽量さ**: 記法さえ覚えれば装飾を伴う文章を素早く書け、「資料作成の高速化」という目的に合致する

ブラウザがMarkdown記法を直接解釈できないため、閲覧時にHTMLへ変換する処理が必須となる。変換処理の詳細は設計書4章を参照。

### 3.6 エラーメッセージの扱いについて

記事の作成・編集等でバリデーションエラー(必須項目未入力等)が発生した場合、ユーザーには日本語で分かりやすいメッセージを表示する必要がある。開発初期はServer Action内で`throw new Error(...)`する実装にしていたが、本番ビルド環境ではセキュリティ上の理由からエラーメッセージの詳細がクライアントに伝わらず、意図しない汎用エラー表示になる不具合が判明した。対策として、Server Actionはエラー時に例外を投げず、`{ error: "メッセージ" }`という戻り値でエラー内容を返す設計に変更した。あわせて、必須項目が全て入力されるまで保存ボタン自体を非活性にすることで、そもそも不正な送信が発生しにくい設計にしている。

## 4. 非機能要件

### 4.1 性能要件

| 項目 | 内容 |
|---|---|
| 応答速度 | 記事一覧・検索結果の表示は体感でストレスのない速度(目安3秒以内)を目標とする |
| 想定同時アクセス数 | 社内利用が前提のため、大規模な同時アクセスは想定しない |

### 4.2 可用性・信頼性

| 項目 | 内容 |
|---|---|
| 稼働時間 | 研修成果物のプロトタイプであり、24時間365日の高可用性は要件としない |
| データ消失対策 | 記事削除は論理削除とし、誤操作によるデータ消失を防ぐ(3.3参照) |

### 4.3 セキュリティ

| 項目 | 内容 |
|---|---|
| なりすまし対策 | 著者記録はUser選択式のため、技術的になりすましは防げない。既知の制約として明記する |
| 外部送信データ | Gamma連携を利用する場合、送信前に「機密情報が含まれていないか」を確認するダイアログを表示する運用とした |

### 4.4 保守性・拡張性

| 項目 | 内容 |
|---|---|
| コード品質 | TypeScriptによる型安全性を活かし、実行時エラーを設計段階で防ぐ |
| 将来拡張 | 認証機能・差分表示・ロールバック・論理削除の実装自動化(soft-deleteライブラリ)・Gamma連携の実API切り替え等は、既存設計を壊さず追加できる疎結合な構成を意識する |
| ドキュメント | 要件定義書・設計書・README・develop.mdを整備し、後任者が触れる状態を保つ(属人化解消という本システムの目的にも合致) |

### 4.5 開発・運用環境

## 5. 認証に関する設計判断(補足)

本システムでは個別ユーザーのログイン機能を実装しない。判断根拠は以下の通り。

属人化解消という目的に必要な「誰が書いたか」の記録は、ログインではなくUser選択式の著者記録(3.2.7)で代替可能と判断した。

なお、第三者による偶発的なアクセスを防ぐ手段として、Vercelの簡易パスワード保護機能(Deployment Protection)の利用も検討したが、無料プランでは利用可能な人数が限られる(自分ともう一名まで)という制約があり、多人数による利用という共有システムとしての使い方にそぐわないため取りやめた。本プロジェクトの主目的が実務知識の習得(1.2参照)にあり、アクセス制御自体の完成度を追求することは目的に含まれないため、現状はアクセス制御を設けない構成とし、代わりに学習内容をmdファイルにまとめた。本番導入時には、認証機能とあわせてアクセス制御の設計が別途必要になる。
