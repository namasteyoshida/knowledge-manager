## 1. DB設計

### 1.1 ER図(テーブル関係)

```
DEPARTMENT ||--o{ USER : belongs_to
USER ||--o{ REVISION : writes
PAGE ||--o{ REVISION : has
PAGE }o--o{ TAG : tagged_with
PAGE ||--o{ GENERATION_REQUEST : source_of
USER ||--o{ GENERATION_REQUEST : requests
```

- `DEPARTMENT`は`USER`に対して1対多の関係を持つ独立したマスタテーブル。組織変更(部署名変更・統廃合)に対応しやすくするための正規化である(1.3参照)
- `REVISION`が`USER`と`PAGE`の両方に外部キーを持つ中間的なテーブルとして機能し、「誰が」「どのページを」「いつ」編集したかを1レコードで表現する
- `PAGE`と`TAG`は多対多の関係(1記事に複数タグ、1タグに複数記事)。未実装(ストレッチ)
- `GENERATION_REQUEST`はGamma連携用で、`PAGE`(任意)と`USER`(必須)にそれぞれ紐付く。実装済み

### 1.2 Prismaスキーマ

```prisma
model Department {
  id    String @id @default(cuid())
  name  String @unique
  users User[]
}

model User {
  id                 String              @id @default(cuid())
  name               String
  departmentId       String?
  department         Department?         @relation(fields: [departmentId], references: [id])
  revisions          Revision[]
  generationRequests GenerationRequest[]
}

model Page {
  id                 String              @id @default(cuid())
  title              String
  createdAt          DateTime            @default(now())
  updatedAt          DateTime            @updatedAt
  deletedAt          DateTime?
  revisions          Revision[]
  tags               Tag[]
  generationRequests GenerationRequest[]
}

model Revision {
  id        String   @id @default(cuid())
  pageId    String
  page      Page     @relation(fields: [pageId], references: [id])
  authorId  String
  author    User     @relation(fields: [authorId], references: [id])
  content   String
  createdAt DateTime @default(now())
}

model GenerationRequest {
  id           String        @id @default(cuid())
  pageId       String?
  page         Page?         @relation(fields: [pageId], references: [id])
  userId       String
  user         User          @relation(fields: [userId], references: [id])
  inputText    String
  status       RequestStatus @default(PENDING)
  resultUrl    String?
  errorMessage String?
  createdAt    DateTime      @default(now())
  updatedAt    DateTime      @updatedAt
}

enum RequestStatus {
  PENDING
  PROCESSING
  COMPLETED
  FAILED
}
```

### 1.3 テーブル定義・設計意図

#### Department(部署マスタ)

| カラム名 | 型 | 制約 | 説明 |
|---|---|---|---|
| id | String | PK, cuid | 主キー |
| name | String | NOT NULL, UNIQUE | 部署名 |

設計意図:当初`User`テーブルに`department`を文字列として直接持たせる案だったが、会社の組織体制(部署名・部署構成)は変更されやすいという実態を踏まえ、独立したマスタテーブルとして正規化した。これにより部署名の変更は`Department`テーブルの1レコードを更新するだけで完結し、部署の新設・統廃合にも`User`側のデータを触らずに対応できる。

#### User(社員マスタ)

| カラム名 | 型 | 制約 | 説明 |
|---|---|---|---|
| id | String | PK, cuid | 主キー |
| name | String | NOT NULL | 氏名 |
| departmentId | String | FK → Department.id, NULL可 | 所属部署 |

設計意図:認証情報(パスワード等)を一切持たない、純粋なマスタデータとして設計。将来認証機能を追加する際も、このテーブルに`email`や`password`カラムを追加するだけで拡張できる。

#### Page(記事本体)

本文(content)を持たない。本文は必ずRevision側に保存する設計にすることで、「記事の本体は常に最新Revisionへの参照である」という一貫したルールを保つ。

#### Revision(改訂履歴)

編集のたびに新規INSERTのみ行い、UPDATE/DELETEは行わない「追記型」の設計。Gitのコミットオブジェクトと同じ思想(過去のスナップショットは不変)を採用している。

#### Tag(タグマスタ、未実装)

想定ユースケース:記事数が増えた際、検索キーワードを知らなくても「業務領域」「資料の種類」といったカテゴリから記事を辿れるようにするナビゲーション手段。1記事に複数タグを付けられる想定のため多対多とする。

#### GenerationRequest(資料生成リクエスト)

Gamma APIへの非同期リクエストの状態(PENDING→PROCESSING→COMPLETED/FAILED)を管理し、生成結果へのリンク(resultUrl)を保持する。`pageId`をnullable(必須にしない)にしているのは、将来的な拡張として記事として保存せず、その場限りの箇条書きから直接資料だけを作りたいカジュアルな利用にも対応するため。失敗時は`status: FAILED`と`errorMessage`を記録する。

### 1.4 論理削除の実装方針

**現行の実装**: 記事を取得する全てのクエリに`where: { deletedAt: null }`条件を明記する、素直な実装とした。学習コスト・実装コストを抑え、コードを読んだ際に「なぜ削除済みが除外されているか」が一目で分かる状態を優先している。

**将来の改善候補**: `prisma-extension-soft-delete`のような論理削除専用のPrisma拡張ライブラリの導入。クエリのたびに条件を書き忘れるリスクを構造的に防げるが、今回は説明のしやすさを優先して見送った。

## 2. 画面設計

### 2.1 画面遷移

```
記事一覧(起点)
 ├─ 記事詳細 ─ 記事編集(保存後は記事詳細へ戻る)
 ├─ 記事作成(自由入力/テンプレート入力をモード切り替え。保存後は記事詳細へ遷移)
 └─ 検索結果(クリックで記事詳細へ遷移)
```

### 2.2 画面一覧

| No | 画面名 | 目的 | 主な要素 |
|---|---|---|---|
| 1 | 記事一覧 | 登録済み記事をブラウズする起点画面 | 記事カード(タイトル・最終更新日・最終更新者)、検索ボックス、新規作成ボタン |
| 2 | 記事詳細 | 記事本文を閲覧する | 本文(HTML変換済み)、著者・更新日時、改訂履歴一覧、編集/削除ボタン、Gammaでスライド化ボタン |
| 3 | 記事作成 | 新規記事を書く(自由入力/テンプレート入力を切り替え可能) | `NewPageSwitcher`によるモード切り替え、`PageForm`(自由入力)または`DocumentTemplateForm`(テンプレート入力、5セクション) |
| 4 | 記事編集 | 既存記事を更新する | `PageForm`と共通コンポーネント。既存本文が初期値として入る |
| 5 | 検索結果 | キーワード検索の結果を見る | 検索ボックス、ヒットした記事のリスト |
| 6 | 予期しないエラー画面 | 想定外の異常発生時の行き止まり画面 | `app/error.tsx`(レンダー中エラー用)、`app/unexpected-error/page.tsx`(イベントハンドラ内エラー用)。操作要素を持たない |

当初、資料構成支援(テンプレート入力)は専用ページ`/pages/new-from-template`として計画していたが、`/pages/new`内でモード切り替えする構成に統合した(3.2参照)。

### 2.3 設計意図

- 記事作成画面と記事編集画面は同一コンポーネント(`PageForm`)として実装する。新規作成時は空のフォーム、編集時は既存Revisionの内容を初期値として渡すという差分のみで両方をカバーする

## 3. Markdown編集機能のコンポーネント設計

### 3.1 責務分担

自由記述モード(記事作成・編集)とテンプレート入力モード(5セクション)の両方で、Markdownツールバー・入力欄・プレビューを再利用するため、以下の3コンポーネントに分離している。

| コンポーネント | 責務 |
|---|---|
| `MarkdownToolbar` | 見出し・太字・箇条書き・リンクのボタンを表示し、押下されたら`onInsert`イベントを通知するだけ。`ref`やDOM操作は一切扱わない |
| `MarkdownField` | `textarea`本体、カーソル位置を扱う`ref`、Markdown記法の挿入処理(`useCallback`で定義)を1つのコンポーネント内に保持する |
| `MarkdownPreview` | 渡された`content`をデバウンス処理(300ms)の後にHTML変換し、プレビュー表示する |

利用側は以下のようにシンプルに組み合わせる。

```
PageForm(自由記述)         → MarkdownField ×1 + MarkdownPreview ×1
DocumentTemplateForm(テンプレート) → MarkdownField ×5 + MarkdownPreview ×1(5セクション結合後)
```

### 3.2 設計変更の経緯:`react-hooks/refs`への対応

当初、`useMarkdownToolbar`というカスタムフックで`ref`と挿入処理(`insertSyntax`)をまとめて返す設計にしていたが、`insertSyntax`を別コンポーネント(`MarkdownToolbar`)にpropsとして渡す構造が、ESLintの`react-hooks/refs`ルール(「レンダー中にref.currentを参照してはならない」)に抵触した。

原因は、「`ref`を保持するロジック(フック)」と「そのrefを使うUI(textarea)」が別コンポーネントに分かれ、`insertSyntax`がコンポーネントをまたいで渡されることで、ESLintの静的解析が安全性を追跡できなくなっていたことである。

対応として、`ref`・`textarea`・挿入処理を`MarkdownField`という1つのコンポーネントに閉じ込め、`MarkdownToolbar`へは「ローカルで定義したコールバック関数」を渡す構成に変更した。これはReactで最も標準的な「親から子へイベントハンドラを渡す」パターンであり、ESLintの静的解析とも整合する。ESLint抑制コメントによる警告の無効化は、構造上の問題を覆い隠すだけで根本対応にならないため採用しなかった。

### 3.3 Markdown記法挿入のロジック

DOM操作(`ref.current`の読み取り)と、文字列組み立てのロジックを分離している。

```typescript
// lib/markdownSyntax.ts(純粋関数、DOM非依存)
export function applyMarkdownSyntax(
  value: string, selectionStart: number, selectionEnd: number,
  before: string, after: string = ""
): { newValue: string; newCursorPos: number }
```

`MarkdownField`は、`textarea`の`selectionStart`/`selectionEnd`を取得してこの関数に渡し、返ってきた`newValue`で状態を更新、`newCursorPos`でカーソル位置を復元する。`requestAnimationFrame`を用いて、Reactの再描画完了後にカーソル位置を設定している。

## 4. Markdown→HTML変換処理

### 4.1 変換パイプライン

remark/unifiedを用い、以下の手順でMarkdownをHTMLへ変換する。

```
Markdownテキスト
  ↓ remark-parse でパース
AST(抽象構文木)
  ↓ remark-rehype でHTML用ASTに変換
  ↓ rehype-sanitize で危険なタグ・属性を除去(XSS対策)
  ↓ rehype-stringify でHTML文字列として出力
HTML文字列
```

DBには常にMarkdown文字列(変換前)を保存し、閲覧時に都度変換する設計とすることで、編集画面に戻す際の逆変換処理を不要にしている。

### 4.2 類似する仕組みとの比較

同様の変換処理は、VSCodeの`.md`ファイルプレビュー機能(`markdown-it`使用)やGitHubのREADME表示でも行われている。使用ライブラリは異なるが、「Markdown文字列を構造化データに変換しHTMLとして描画する」という処理の本質は共通している。

## 5. API設計

### 5.1 基本方針

| 手段 | 用途 |
|---|---|
| Server Component + Prisma直接呼び出し | 一覧・詳細・検索など読み取り全般 |
| Server Actions | 作成・更新・削除など書き込み全般 |
| Route Handler(API Route) | 非同期処理の状態確認(Gamma生成のポーリング)など、クライアントから繰り返し呼び出す処理 |

### 5.2 Server Actionsのエラー通知方式

**設計変更(重要)**: 当初、バリデーションエラーは`throw new Error(...)`で通知する設計だったが、本番ビルド環境ではNext.jsの仕様上、Server Actionから投げられた生のエラーメッセージがセキュリティ上の理由でクライアントに伝わらず、汎用エラー(React error #441)に置き換えられる不具合が判明した。

対応として、Server Actionはバリデーションエラー時に`throw`せず、`{ error: "メッセージ" }`という戻り値を返す方式に統一した。呼び出し側(Client Component)は戻り値の`error`プロパティを確認し、あれば画面に表示、なければ正常系の処理を行う。

```typescript
export async function createPage(title: string, content: string, authorId: string) {
  if (!title || !content || !authorId) {
    return { error: "タイトル、本文、著者は必須です。" };
  }
  const page = await prisma.page.create({ data: { title, revisions: { create: { content, authorId } } } });
  revalidatePath("/pages");
  return { page };
}
```

`throw`(例外)は「予期しない異常事態」を表すためのものであり、「入力必須です」のようなユーザー操作起因の想定内のエラーには戻り値方式が適切、という設計思想に基づく。あわせて、フォーム側では必須項目が全て揃うまで送信ボタンを非活性(`disabled`)にする制御を追加し、そもそも不正な送信が発生しにくい設計にしている。

なお、この方針転換はサーバー内部の関数間(例:`GammaGenerator`→`processGeneration`)でのエラー伝達には適用しない。クライアントに直接エラーを返す経路にのみ関係する設計判断である。

### 5.3 主なServer Actions

| 名称 | 入力 | 処理 | 戻り値 |
|---|---|---|---|
| `createPage` | title, content, authorId | Page新規作成+初回Revision作成(トランザクション) | `{ page }` または `{ error }` |
| `updatePage` | pageId, content, authorId | 新規Revisionを追加、Pageの`updatedAt`を更新 | `{ success }` または `{ error }` |
| `deletePage` | pageId | `deletedAt`にタイムスタンプ設定(論理削除) | なし |
| `createPageFromTemplate` | title, sections(5項目), authorId | セクションをMarkdown化(`composeTemplateMarkdown`)し`createPage`を呼び出す | `createPage`と同じ |
| `requestGammaGeneration` | inputText, userId, pageId? | `GenerationRequest`を作成し、バックグラウンドで生成処理を開始 | `{ requestId }` または `{ error }` |

`createPageFromTemplate`は内部で`createPage`をそのまま呼び出す構成にすることで、コードの重複を避けている。

### 5.4 Gamma連携:非同期処理の設計

**`DocumentGenerator`抽象化レイヤー**:実際の生成処理を`DocumentGenerator`インターフェースとして抽象化し、動作確認用の`MockGenerator`(3秒後にダミーURLを返す)と、実際のGamma API呼び出しを行う`GammaGenerator`(雛形のみ、有料プラン未加入のため未検証)の2実装を用意した。使用する実装は`document-generator/index.ts`の1行で切り替えられる。

```typescript
export const documentGenerator = new MockGenerator();
// 本番切り替え時: export const documentGenerator = new GammaGenerator();
```

**非同期処理フロー**:

```
1. requestGammaGeneration が GenerationRequest(status: PENDING)を作成し、
   requestIdを即座に返す(生成完了を待たない)
2. processGeneration がバックグラウンドで status を PROCESSING に更新し、
   documentGenerator.generate() を実行
3. 成功時: status: COMPLETED, resultUrl を保存
   失敗時: status: FAILED, errorMessage を保存
4. クライアントは /api/generation-requests/[id] を2秒間隔でポーリングし、
   status が COMPLETED/FAILED になったら結果を表示
```

**Vercel(Serverless)環境における実行時間の制約**: `processGeneration`をawaitせずバックグラウンドで実行する設計は、ローカル開発環境(Node.jsプロセスが常駐)では問題なく動作するが、Vercelのサーバーレス実行環境では、クライアントへのレスポンスを返した後もバックグラウンド処理が継続される保証がない。本番で実際にGamma APIと連携する場合は、Vercelの`waitUntil()`(レスポンス後も処理継続を明示する仕組み)の利用、または外部のジョブキューサービスへの処理委譲を検討する必要がある。今回はモック実装(数秒の遅延のみ)のため実害はないが、本番切り替え時の設計課題として認識している。

**送信前の確認ダイアログ**:生成ボタン押下時、`window.confirm`で「機密情報が含まれていないか」の確認を挟む設計にした。要件定義書4.3の運用ルールを、システム側でも補強する狙いである。

### 5.5 ポーリング用Route Handler

```typescript
// app/api/generation-requests/[id]/route.ts
export async function GET(req: Request, { params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const request = await prisma.generationRequest.findUnique({ where: { id } });
  return NextResponse.json({ status: request.status, resultUrl: request.resultUrl, errorMessage: request.errorMessage });
}
```

`[id]`という角括弧付きのフォルダ名が、Next.jsに動的パラメータであることを伝える特別な意味を持つ。

### 5.6 同時編集に関する既知の制約

複数人が同時刻に同じ記事を編集した場合、後から`updatePage`を実行した側の内容が最新Revisionとして表示される。Revisionは追記型のため、先に保存された内容がデータとして失われることはなく、改訂履歴からは辿れる。楽観的ロックの仕組みを`updatePage`に追加することで競合を検知できるが、今回のスコープでは実装せず将来の改善点とする。

## 6. デプロイ構成

### 6.1 環境ごとのDB接続

```
開発環境: Next.js → Prisma → Docker上のPostgreSQL
本番環境: Next.js(Vercel) → Prisma → Neon上のPostgreSQL
```

ローカルの`.env`とVercel側の環境変数を分離し、それぞれ異なる`DATABASE_URL`を設定している。

### 6.2 ビルドコマンド

```json
"build": "prisma generate && next build"
```

Vercel環境ではpnpmのセキュリティ機構により、`@prisma/client`インストール時の`postinstall`スクリプト(`prisma generate`を自動実行するもの)が実行されないことが判明したため、ビルドコマンドに明示的に`prisma generate`を組み込んでいる。

### 6.3 マイグレーションの反映

`schema.prisma`を変更した際は、ローカルの`migrate dev`に加えて、Neon(本番)側にも`migrate deploy`を別途適用する必要がある。この反映漏れが、開発中に複数回不具合の原因となった(develop.md参照)。
